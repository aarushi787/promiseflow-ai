# MVP scope and manufacturing assumptions

**Historical V1 scope below:** V3 supersedes overtime costing, background jobs, onboarding, quality holds and decision context. Refer to [KNOWN_LIMITATIONS](KNOWN_LIMITATIONS.md), [SCENARIO_ENGINE](SCENARIO_ENGINE.md) and [V3_IMPLEMENTATION_REPORT](V3_IMPLEMENTATION_REPORT.md) for current capability boundaries.

## Delivered

All fifteen requested navigation modules are implemented. Sales can evaluate a new commitment, planners can edit typed factory data and propose plans, supervisors can inspect dispatch operations, purchase/maintenance can simulate disruptions, and managers can approve a version. Reports and audit information come from persisted solver results.

The sample automotive pack contains 12 customer orders, 5 customers, 3 products, 3 routings, 8 production/vendor resources, shared tooling and an operator crew, 3 materials, 2 suppliers and two calendars. The engine uses no industry-specific branching. Other industries can be represented by configuring resources and routings. Industry selection itself is a label, not an automatic industry-pack installer.

What-if supports resource breakdown/maintenance/production delay, material delay/expedite/quality hold, supplier delay, operator absence, extra shifts/overtime, quantities, due dates, forced qualified alternative resources/outsourcing and transfer-batch splitting. Rush orders use the Promise Checker and its recovery solve; the API also accepts a rush-order scenario.

Outsourcing does not invent vendor capability: the route must already list a qualified external-vendor resource. Alternate-machine scenarios similarly restrict only operations already eligible for that resource. Transfer-batch splitting changes the product’s transfer-batch size across its orders. Overtime extends the selected resource calendar across the horizon, not just one date; it does not silently add qualified staff.

## Deliberate limits and extension points

| Area | MVP behavior / limit |
|---|---|
| Optimization quality | Bounded deterministic CP-SAT search. Feasible is not necessarily optimal. Earliest is claimed only for an optimal candidate-completion solve with the current plan frozen. |
| Material | One incoming lot per material; full-order reservation at first release. Deterministic priority allocation is conservative and not jointly optimized. `reserved` represents stock unavailable to these active modeled orders, avoiding hidden double counting. |
| Time | Naive plant-local timestamps; demo epoch is fixed in the active version. No multi-timezone or daylight-saving scheduling. Set the planning start date in Settings to advance the epoch; complete or reconcile historical locked work before advancing. |
| Setup | Fixed setup per operation alternative and transfer batch; no predecessor-dependent changeover matrix or cleaning validation. |
| Batches | Transfer batches, not process-vessel co-batching. Operations are nonpreemptive. No partial-batch dispatch commitment. Operation `batch_size` is descriptive; product `batch_size` controls transfer splitting. |
| Precedence | Linear routing sorted by sequence, not arbitrary dependency DAGs. Transfer/queue lag follows each operation. |
| Tools/operators | Capacity-constrained individual resources/crews, skill and eligibility checks, calendars and absence. No labor-payroll or multi-skill combinatorial crew assembly. Resource efficiency affects processing duration; separate operator efficiency is not implemented. |
| Vendors | Capacity, lead/transit time, resource/route rates. Supplier reliability is recorded, not treated as a probabilistic guarantee. |
| Execution | Manual order status; released/in-production work is frozen. No actual-operation start/finish ingestion, scrap/rework tracking, inventory decrement, delivery transaction or live schedule adherence. |
| Explanations | Deterministic observed material, capacity and external-process constraints. No falsely additive causal delay attribution; no counterfactual proof for each factor. |
| Costs | Resource hourly cost and optional route unit cost. Overtime allowance is conservative; outsource/expedite quotes, SLA penalties and payroll are not fully costed. |
| Objectives | Weighted lateness, tardiness, makespan and production cost. Idle time, WIP, setup-change count and overtime are not separate optimized terms. |
| Scope | Maximum 1,200 batch operations per solve. Single plant and tenant. Every active order must be scheduled before activation. |
| Onboarding | XLSX/CSV preview, validation and apply. Orders use a dedicated form; complex masters use an advanced JSON editor and spreadsheet templates. |
| Copilot | Optional LLM layer not enabled. No schedule, external message or factory mutation is generated by an LLM. |

## Reporting semantics

“On time” means projected completion has at least the configured delivery buffer. “At risk” means projected on-time completion has insufficient buffer, or a promise solve cannot prove the requested date infeasible and has not found an on-time candidate. “Late” is a projected schedule outcome, not a recorded customer delivery failure. Unscheduled orders have explicit reasons and prevent activation.

Utilization is occupied resource-minutes divided by available capacity-minutes over the first seven days, excluding maintenance. Because finite capacity is enforced, a feasible plan will never show a physically impossible utilization over 100%; overload pressure manifests as backlog and late orders. Current dashboard adherence is intentionally not invented without execution data.
